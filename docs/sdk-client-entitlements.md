# Client entitlement boundary

Protocol extensions can need independent client permissions beyond fixed List, Launch, View and Terminate selectors. A component grant authorizes a module, not a remote client. This generic contract enables separately approved operation names; protocol semantics, session ownership and effect fencing remain the consumer's responsibility.

Identity 1.2 appends a synchronous check to the selected identity provider. The trusted protocol owner maps each operation to a fixed entitlement from trusted composition, verifies TLS possession, and passes that connection's certificate and the exact name. Names have a lower-case ASCII reverse-DNS namespace with at least two segments, followed by `/` and an operation segment; segments allow letters, digits, hyphens and underscores. Maximum name length is 128 bytes. Trusted administrators allocate namespaces and approve the exact names and their meaning; plugins must coordinate ownership with administrators. There is no automatic ownership proof or registration: a module declaration never grants a client access. If two components use the same name they deliberately share the same policy; trusted composition or the operator must prevent unintended collisions; this contract does not implement that validation. Native plugins are trusted code, not sandboxed.

The pairing administrator can replace one client's bounded list using `update_client_entitlements`, certificate fingerprint, and `expected_revision`; only the existing administrator principal may write it. Empty/missing lists deny all, including when legacy permission mode is disabled. Existing permissions and old documents retain their behavior. Malformed names and duplicates are rejected. No name is implicitly approved or inherited. Unknown, unapproved, unpaired, expired, or unavailable authority never authorizes; every non-OK result denies. Bind minor 2 and full table size, and deny if unsupported. The input bytes are borrowed only for the call.

The authority reads a committed snapshot and verifies it remains current before returning. A policy mutation invalidates it while pending; subsequent checks see revocation after commit. A successful check is not a lease and cannot cancel or fence a concurrent effect. Consumers must recheck at appropriate effect and delivery boundaries and provide any stronger in-flight revocation, lifecycle and stream-ownership guarantees their operations need. The existing legacy permission checks remain separately required where applicable.

The Rust callback signature is `unsafe extern "C" fn(context: *mut c_void, certificate_der: BorrowedBytes, name: BorrowedBytes) -> Status`, exposed as `IdentityApiV1_2::check_entitlement` after the `IdentityApiV1_1` prefix. The C equivalent is `AmaterasuStatus (*check_entitlement)(void *context, AmaterasuBorrowedBytes certificate_der, AmaterasuBorrowedBytes name)` in `AmaterasuIdentityApiV1_2`. Consumers request `amaterasu.identity/1`, major 1, minimum minor `INTERFACE_MINOR_ENTITLEMENTS` (2), and `sizeof(IdentityApiV1_2)`, validate the returned table version and size, and retain the binding through each call. Use its `v1_1.v1_0.base.context`; release only after all concurrent calls finish. Both input buffers are borrowed synchronously. Check the verified connection certificate against the operation's trusted configured name; authorize only `STATUS_OK`. Unknown names return forbidden, malformed names invalid argument, unpaired or invalid certificates untrusted, and unavailable policy unavailable. Treat unsupported binding and all non-OK results as denial.

A trusted configuration assigning meanings to names must reject ambiguous or unintentional reuse before enabling those operations. Pairing's client-grant configuration rejects duplicate names in one grant list; it has no cross-component declaration or operation-mapping configuration to validate. Explicitly sharing one name means sharing the same client policy and must be an intentional administrative decision.
